## Payout Sheet 📊

Payout data is read from the `Combined` sheet over the `A:ZZ` range.

- Row 1 contains guild IDs, each marking the start of that guild's payout columns.
- Row 2 contains the payout headers: `Pending`, `Share Ready`, and `Distributed`.
- Column A contains Discord tags, such as `@username`.

For `/payout`, the bot finds the matching Discord tag in column A, selects the status columns belonging to the server where the command was run, and displays those three values. Empty or invalid cells are treated as `0 z`.

For `/payoutsummary`, the bot selects that guild's `Pending`, `Share Ready`, or `Distributed` column according to the `amount` parameter, includes every non-zero row, calculates the displayed total, and applies the requested sorting options.

`/stats` reads the configured guild worksheet and scans titled run columns from row 5, including historical runs. It matches each title against that guild's configured instance names, initials, and keywords; unmatched titles go to `Others`. Overall (the default) sums purple Pending, yellow Share Ready, and green Distributed participant cells. Other amount choices select just one of those colors. Shares are summed by matched instance; combined runs contribute to each matched instance. Alphabetical instance fields show the truncated amount. Personal shows joined / all titled runs for that instance; Guild shows all titled runs for that instance. A final `📋 TOTAL` sums each run once, without double-counting combined titles; Personal shows joined / all titled runs and Guild shows all titled runs. In Personal mode, TOTAL also shows Impact as the user's share of the whole guild total, plus Rank by amount among sheet players (higher amounts rank first; ties share a rank). `which:Ranking` shows the top 10 players for the selected amount, using separate medal fields for the top three and a `✨4th-10th` field for the rest. Entries use escaped Discord display names as plain, non-pinging text. Ranking impact is a percentage of the guild total, and the 4th–10th ranks are shown before each name. The `🎖️Your Rank` field shows the invoking user's selected-amount total and guild impact, even when they are outside the top 10. The Guild embed uses 📊 with the guild name as author and uses the guild icon as thumbnail. After the total, Personal and Guild display a small-text note warning that combined signups (for example, B2B ET+EC) can cause the total to differ from the sum of instance types, saying statistics are subject to change, and thanking users for joining; Ranking omits that field. The embed color reflects the selected amount. `which:Personal` is the default and uses the invoking user unless `user` selects another member. `which:Guild` sums all members and cannot be combined with `user`. The `user` option is only available with Personal. The optional `sendprivately` option follows `/payout`.

`/changesharevendor` and `/changeshareparticipants` only work in bot-generated payout threads in the configured `payoutSheetChannelId` forum. `/changesharevendor` replaces the vendor label with the supplied text, including `n/a` or `none`. `/changeshareparticipants` shows the current roster to copy, then accepts the updated party and Discord mention lines as the invoking user's next message in that thread. It recalculates Participants from unique mentions, adds newly listed users to the thread, removes users no longer listed, and updates the roster post.

`/set share status status:<choice>` finalizes only the payout thread where it is invoked. Choices are `Ready for distribution`, `Done (no share)`, and `Cancelled`. Only the organizer identity saved with that specific export or a member with Manage Server can use it, and only for a complete managed export whose latest Sheets sync succeeded. `/export` snapshots the organizer ID, name, and avatar for each run; later organizer changes on a signup do not change ownership of existing payout threads. Legacy/unmanaged exports require manual updates; pending or failed managed exports must first be successfully synchronized with `/export`. A new finalization requires the pending `⏳` title. Once a Sheets write has been attempted, the status cannot be changed; an interrupted run may resume only that same status. If preflight fails before any write is attempted, the saved selection is cleared: vendor/roster edits, `/export` synchronization, and selecting a different status remain available.

The bot needs **Manage Threads** and **Send Messages in Threads** in the payout forum. Ready changes purple cells in the exact Export ID column to `#FFD966`, then writes an adjacent blank-column insertion and deletion as separate Sheets batches to trigger custom formulas. It rereads the worksheet and confirms the participant cells are effectively yellow and both per-run and Combined Share Ready values are evaluated before sending DMs. A participant is not DM'd when either their run share or total unclaimed balance is negative; notification preferences set Off also suppress that participant's DM. `/set notification setting setting:On|Off` stores a per-user, per-guild preference that defaults to On and currently controls only Ready share-status DMs. Eligible DMs contain the run name/date and participant name, plus a yellow claimable embed with truncated `This run` and `Total unclaimed` values and payout instructions. The public response reports `Share status: ✅ Ready for distribution` and the confirmed `SheetName (ColumnName)`, including the number of DMs skipped for negative balances or disabled preferences. It adds **Total earned** (row 6), less **Reimbursements** (row 8), their difference, and a participant breakdown using saved exported display names (not tags or mentions) and each participant's evaluated run share from row 10 onwards. All amounts come from the exact Export ID column in the invoking guild's configured worksheet, not a hardcoded test sheet; displayed zeny is comma-separated and truncated to whole zeny, matching DMs. Totals and shares are saved together before notifications so interrupted reporting can resume without rereading Sheets. Missing or unevaluated totals prevent confirmation and Ready DMs; older saved finalizations without totals explicitly report the summary unavailable. Long breakdowns are split into Discord-sized messages.

Done (no share) requires the organizer to manually clear all participant values and formulas in the exact run column from row 10 onwards before invoking the command. Even literal zero and formulas evaluating to zero or empty text must be removed; the bot reports the first uncleared cell and does not write. The blank participant cells are verified again after finalization. It changes purple cells to green (`#00FF00`) and triggers recalculation, but sends no DMs and never clears financial values itself. This prevents green-counting Distributed formulas from counting participant amounts for a no-share run. Cancelled deletes only that exact run column and rereads the sheet to verify its Export ID metadata and note are gone. The public response names the confirmed sheet column and the thread is locked without intentional archiving.

Ready balance verification allows a shortfall of up to 1 zeny for rounded or truncated Combined formulas. Evaluated amounts are polled up to eight times at two-second intervals (14 seconds of waiting), without repeating Sheets writes; larger shortfalls and unevaluated formulas still prevent confirmation.

The Ready payout summary is sent as a separate thread message after the thread lock succeeds, not as part of the command's success reply. If locking fails, the summary waits until a successful retry. Summary chunks have separate saved delivery progress so retries do not duplicate sent or uncertain deliveries.

Sheets finalization and its saved result share the same queue as vendor/roster mutations, so edits are checked and applied before finalization or rejected afterwards. DMs, public reporting, title changes, and thread locking run outside the spreadsheet and guild history queues; each progress write briefly reacquires the history queue. A separate per-thread queue prevents duplicate finalizations. If the temporary recalculation column may remain after a failed insertion/read/deletion, the saved public error names its A1 column letter for manual inspection and removal.

Sheets failures do not stop Discord completion, but the bot will state that the sheet action is unconfirmed and will not claim recoloring or removal succeeded. If colors or evaluated values cannot be confirmed after the separate recalculation writes, Ready DMs are skipped; the organizer must correct Sheets and notify participants manually. Do not retry the status command as a Sheets repair. Blocked DMs do not prevent completion and are listed with mentions suppressed. An interrupted DM is reported as uncertain and is not automatically resent. The bot persists progress across history, Sheets, title, public report, DM, and lock steps; because these systems do not share a transaction, inspect partial outcomes and follow the reported manual instructions. Finalizing disables later vendor/roster edits and export synchronization for that run.

### Export Spreadsheet Synchronization

After a confirmed Discord export, the bot selects a worksheet using `payoutWorksheets` in `private/discord_settings.json`, within the same spreadsheet selected by `GOOGLE_SHEETS_ID`. The configured mappings are in the json file. Unmapped guilds remain Discord-only; an absent mapping defaults to empty. Each post uses the first empty run column from F up to the dynamically located `Unclaimed` header, filling available space beside existing runs. Columns containing values, formulas, notes, or column metadata are not reused. Only when no empty run column remains does the bot insert a new column immediately before `Unclaimed`. Existing exports are not automatically moved. Combined-instance posts use joined instance initials and split posts use their individual initials, followed by the run's timezone-aware `DD/MM` date.

Each new entry also inserts one empty run column immediately to its right, replenishing available space: one blank column for a normal export and two across a two-part split. Its run area is reset to white, then only row 9 formatting is copied from the adjacent entry to preserve the black header band. No values, formulas, or purple participant backgrounds are copied into the blank column. Summary ranges adjust for these insertions; retries and later vendor/roster edits do not add more blank columns.

Row 5 holds the title; rows 6 and 8 start at numeric zero; row 7 holds the vendor. Rows 6, 8, and participating cells are purple (`#8E7CC3`). Each unique participant receives a formula such as `=(CN$6-CN$8)/9`. Tags match column C case-insensitively with or without `@`. Missing participants are added after the last lifetime roster entry with display name, `Y`, and a literal `@username`; missing `Combined` entries receive the tag plus formulas and formatting copied from the preceding participant. Numeric balances and historical run shares are never copied. Combined template formulas must use a relative reference to their own row's tag; fixed-row references, ambiguous identities, occupied append rows, and unsupported summary formulas stop synchronization before any write.

When appending a guild participant, a prefilled formula under the dynamically located `Share Total` header in row 9 does not mark the row as occupied if it matches the safely rebased template. A missing or invalid Share Total template blocks the append. Cells under the right-side `Name` and `Discord` headers beyond `Unclaimed` are populated with the new participant's identities. Other formulas, manual values, and left-side identity or historical-share data still block the append; these exceptions do not apply to `Combined`. Existing Combined participant rows, as well as new rows, must contain valid lookups for the mapped guild worksheet.

Export IDs are stored as column-scoped Sheets developer metadata, so retries locate the same column even after other columns move. Sheet writes are serialized across all mapped guilds and sent as a single validated batch per post. Failed or uncertain attempts retain every potentially applied roster in export history until confirmation; rerunning `/export` retries pending work without recreating Discord threads or blindly inserting columns. The complete set of populated share rows must match a known roster before rewriting; extra or cleared shares require manual updates. Older exports without managed Sheets history are not linked by title/date guessing. Incomplete Discord roster delivery blocks sheet creation until the roster is repaired.

`/changesharevendor` also updates row 7 of the linked sheet column. `/changeshareparticipants` updates saved vending membership and the pending run's formulas, adds new lifetime identities, and clears removed participants only in that run. Existing totals/reimbursements and lifetime participant records are preserved. Yellow/green or manually overridden shares require manual sheet updates instead of automatic recalculation. A failed sync does not undo a successful Discord edit; repeating an edit can retry its pending sheet work.

Retained participants are matched by Discord user ID against saved member identities. When a tag changes, synchronization reads all worksheets and migrates the existing guild, mirrored Discord, and Combined identities in the same batch without moving financial cells. Missing, colliding, or unsupported identities and lookup sources require manual updates instead of splitting a member's historical balances. History persistence failures warn that Currently Vending may be stale and, for mapped guilds, that Sheets synchronization is unconfirmed.

Every Sheets attempt reports its outcome publicly. A successful update reminds the organizer that cell formulas are defaults and should be reviewed and adjusted if needed. Permissions, layout, formula, or API failures leave Discord successful and ask the organizer to update Google Sheets manually. Read and write requests have 15-second timeouts; writes do not retry automatically after uncertain responses. Treat the bot as a single writer, avoid manual structural edits during export, and verify the configured tabs on a copied spreadsheet with authentic formulas before enabling production use. Unsupported text-based formula ranges must be adjusted manually; the bot does not guess replacements for custom financial formulas.
